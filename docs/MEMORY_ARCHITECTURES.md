# Agent memory architectures: vector, graph, episodic, hybrid — and where Irises sits

> Research note, compiled **2026-08-28**. Sources: [mark-agent](https://github.com/Mazees/mark-agent) (GitHub repo — read from source, not the README), [Agent Memory Architectures: Vector, Graph, Episodic](https://www.digitalapplied.com/blog/agent-memory-architectures-vector-graph-episodic) (Digital Applied blog), [Vector vs Graph vs Episodic: A Tour](https://www.ratkonikolic.com/p/vector-vs-graph-vs-episodic-a-tour) (Rat Konikolic blog). Load-bearing claims in both blogs were traced to primary sources (Mem0's and Zep's own papers) and checked; both held up. Irises' own memory system was read directly from `src/memory/` and `src/db/repositories/` — every claim below carries a file:line citation.

## TL;DR

Irises' memory system belongs to none of the three canonical families cleanly — it is a **hand-rolled tiered store** (recency-windowed short tier → capped structured medium tier → one free-form long-tier document, plus a cold lexical archive) rather than a vector store, a knowledge graph, or an OS-paging episodic manager. If it must be filed under one label, it is closest to the **episodic/working-memory family** (a single self-edited "core memory" document, à la MemGPT/Letta) crossed with a **structured-facts store** (à la Mem0's fact extraction, but file-based instead of vector-indexed) — with **zero graph structure** and **zero embeddings anywhere in the codebase** (confirmed by grep across `src/`).

Where Irises is **stronger** than the textbook architectures for its actual use case (one user per engine instance): it has no vector-collision/contradiction problem (facts are explicitly superseded, not left to float as competing embeddings — `src/db/repositories/memoryMedium.ts:453-479`), no infra to run (SQLite + flat markdown files, no embedding model, no graph DB), and an explicit fail-loud vs. best-effort policy per tier that most hobby implementations (including mark-agent) don't bother with.

Where Irises is **weaker**: it has no semantic recall. `recall_memory` — the one tool that reaches into cold history — is keyword search (SQLite FTS5/bm25, falling back to `LIKE`; `src/db/repositories/memoryArchive.ts:267-299`), so a paraphrased query ("that lake house thing") that shares no tokens with the original entry will miss it, something even a cheap local embedding model (mark-agent's approach) would catch. It also has no multi-hop reasoning and no entity graph (irrelevant for most companion use, but a real gap if Irises ever needs to reason about *relationships between* the people a user mentions). And its "episodic" layer is one document rewritten wholesale by an LLM every couple of minutes, not a formal paging/eviction algorithm.

## 1. Vector / semantic memory

**What it is.** Conversational content (or extracted facts) is embedded and stored in a vector index; retrieval is nearest-neighbor similarity search against the current query's embedding. This is RAG applied to an agent's own interaction history. The canonical production example is **Mem0**.

**Primary-source check.** Mem0's own paper (Chhikara et al., ["Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory," arXiv:2504.19413](https://arxiv.org/abs/2504.19413)) reports Mem0 achieves **91% lower p95 latency and >90% lower token cost than a full-context baseline on the LoCoMo benchmark**, plus a 26% relative improvement over OpenAI's own memory feature on an LLM-as-judge metric. Both blogs cite this figure and it checks out against the paper — the digitalapplied piece doesn't repeat the number but doesn't misstate it either; the ratkonikolic piece quotes it correctly.

**Strengths** (per both sources, consistent with the paper): fast to integrate, efficient token usage relative to stuffing full history into context, strong at single-fact "what did they tell me" lookups, scales horizontally.

**Weaknesses** (ratkonikolic, elaborated): **no native contradiction handling** — "two contradictory facts embed to nearly the same vector," so a stale fact and its correction can both surface with similar scores; multi-hop and temporal reasoning ("who manages X now, after the reorg") are awkward because a vector index has no notion of supersession or ordering; extraction errors compound silently since a wrong fact, once embedded, persists and keeps getting retrieved until something explicitly deletes it; unbounded growth with no native forgetting mechanism. digitalapplied adds a sharper framing: **"Retrieval, not generation, is the bottleneck: most agent memory failures look like hallucinations but are actually retrieval misses."**

## 2. Graph / temporal knowledge graph memory

**What it is.** Facts are stored as typed nodes and edges, often with validity timestamps, so the system can answer multi-hop questions and track how facts change over time. The canonical example both blogs point to is **Zep**, built on the open-source **Graphiti** engine.

**Primary-source check.** Zep's own paper (Rasmussen et al., ["Zep: A Temporal Knowledge Graph Architecture for Agent Memory," arXiv:2501.13956](https://arxiv.org/abs/2501.13956)) confirms the **bi-temporal model**: each fact carries both a validity interval (`t_valid`/`t_invalid` — when it was true in the world) and a system interval (`t_created`/`t_expired` — when Graphiti recorded/superseded it). Superseded facts are invalidated, never deleted, so history is queryable. The paper reports beating a MemGPT baseline on the **Deep Memory Retrieval (DMR)** benchmark (94.8% vs. 93.4%) and up to 18.5% accuracy gains with 90% lower response latency on its own harder benchmark. ratkonikolic's summary of this is accurate; digitalapplied doesn't cite the benchmark numbers at all, just the architecture.

**Strengths:** correctly handles fact supersession ("the downgraded customer, the moved deadline, the role that changed" — ratkonikolic's phrasing), clean multi-hop entity reasoning, auditable timeline of what was true when.

**Weaknesses (both sources agree):** high schema-design cost up front, LLM-based entity/relation extraction is unreliable (fuzzy/paraphrased queries usually need a vector layer bolted on anyway — digitalapplied explicitly notes graph-only setups end up hybrid for this reason), and building/maintaining the graph is genuine engineering overhead, not a drop-in.

## 3. Episodic / working memory

**What it is.** Rather than indexing raw history, the agent maintains an evolving, self-edited representation — a persona block, a running summary, a scratchpad — that it rewrites as the conversation grows, preserving the gist over the verbatim transcript. The canonical example is **MemGPT / Letta**.

**Primary-source note.** MemGPT (Packer et al., October 2023) treats the LLM context window as RAM and an external store as disk, giving the model function calls to explicitly move information between "core" (always-in-context) and "archival"/"recall" memory — an OS-paging metaphor. Letta is the productized descendant. Neither blog cites benchmark numbers for this family beyond DMR (which is really Zep vs. a MemGPT baseline, not a MemGPT self-report); their claims about the OS-paging design and Letta's fit for "long-running conversational agents" match the well-established MemGPT framing.

**Strengths:** coherent long-running sessions, resumable tasks, narrative continuity across weeks — the agent always has *a* current picture of the relationship, never a cold blank.

**Weaknesses:** higher latency for a single fact lookup (you get the gist, not an indexed fact store), cross-episode queries need a secondary index anyway, and repeated summarization causes **"summarization drift"** — details quietly eroding across successive rewrites, which digitalapplied calls out explicitly as this family's characteristic failure mode.

## 4. Hybrid architectures, and what mark-agent actually builds

**The blogs' consensus on hybrids.** Both articles converge on the same conclusion independently: nobody ships one architecture in production. digitalapplied: **"The production pattern we see most often in 2026 is not a single architecture but a small stack"** — vector + short episodic buffer, vector + graph for entity-heavy domains, or all three. ratkonikolic recommends pairing "episodic working memory (for the coherent gist) with a temporal graph (for facts that must stay correct as they change)," reserving plain vector stores for "what does the corpus say" rather than "what do I know about this user." Both also flag that the real cost of any of this is **engineering/tuning time, not infrastructure** — digitalapplied: "Infrastructure is rarely the expensive part... the dominant costs are engineering time and ongoing tuning."

**mark-agent's actual implementation** (read from source, not its README — the README's one-liner, "Vector Memory dan Relational Growth System," undersells what's actually there):

- **Storage & embedding.** Durable memory rows live in a Dexie (IndexedDB) table (`src/renderer/src/api/db.js`); at app start they're **hydrated into an in-memory [Orama](https://github.com/oramasearch/orama) vector index** with four separate collections — `memoryIndex`, `archiveIndex`, `documentIndex`, `turnPairIndex` — each with a 384-dimension `vector` field (`src/renderer/src/api/oramaStore.js:12-56`). Embeddings are generated **locally, in-browser/in-process**, via Transformers.js running `Xenova/paraphrase-multilingual-MiniLM-L12-v2` in a Web Worker (falling back to the main thread) — no external embedding API call (`src/renderer/src/api/vectorMemory.js:1-92`).
- **Retrieval.** `searchExtendedMemory`/`executeMemorySearch` embed the query, run cosine similarity (`vecA·vecB` on pre-normalized vectors, `vectorMemory.js:131-137`) against the `notes`/`learn` memory kinds and the turn-pair index, with a caller-tunable similarity threshold (default 0.5) and result limit (default 5) (`vectorMemory.js:159-209`). Two memory *types* — `profile` and `preference` — are treated as **"core memory"** and returned unconditionally with no similarity filter at all (`vectorMemory.js:139-157`) — i.e., mark-agent also keeps a small always-injected tier exactly like Irises' medium/long tiers, on top of the vector-retrieved tier.
- **Writing / consolidation.** New memories are written directly (not shown in the files reviewed here, but referenced by the groomer's `keep_id`/`delete_ids` contract). Separately, a scheduled or triggered **"Hippocampus Engine"** batch job (`src/renderer/src/api/ai/memoryGroomer.js`) sends clusters of similar/chronologically-linked memories to an LLM with an explicit **merge-then-prune** instruction: never delete history, fold an old fact and its update into one chronological sentence (its own example: "used Laptop A" + "now uses a 4090" → "currently uses a 4090, after previously using Laptop A"), pick one row to keep, and mark the rest for deletion (`memoryGroomer.js:30-57`). This is a genuine **consolidation/deduplication pass**, closer to Mem0's LLM-mediated fact updates than to anything in Irises (Irises' closest analog, `upsertFact`, only overwrites a single named key — it has no similarity-based clustering of free-text notes).
- **The "Relational Growth System"** (the other half of the README's claim) is not memory of facts at all — it's a **slowly-drifting personality/relationship model**: five 0–1 traits (`warmth`, `sarcasm_level`, `trust`, `energy`, `obedience`), re-evaluated by an LLM after interactions, clamped to **±0.05 drift per evaluation**, with hard floors on `warmth`/`trust` (0.15) so the persona can cool off but never go irrecoverably cold, gravitating back toward 0.5 baseline when untouched, and — notably — an explicit **anti-manipulation rule**: an *explicit* user request to change a trait ("stop being sarcastic," "trust me more") is defined to NOT count as evidence and is rejected outright; only organic behavioral patterns move the dial (`src/renderer/src/api/ai/relationship.js:1-105`). The same pass can also mint a `new_relational_memory` note on genuinely significant moments (a stated life change, first real emotional disclosure), gated to be `null` unless the moment clearly qualifies (`relationship.js:53-56`, `107-170`).

So mark-agent is a **tri-part hybrid**: local vector search (Mem0-family) + LLM consolidation/dedup (episodic-adjacent) + a bespoke persisted trait-drift model that has no equivalent in either blog's taxonomy and no equivalent in Irises' memory tiers.

## 5. Irises' actual memory system

Irises has **no vector index and no graph** anywhere in `src/` (verified: `grep -ril "embedding|vector|pgvector|cosine|faiss|pinecone|chroma"` across `src/` returns nothing). It is a four-tier system, entirely SQLite + flat files, with retrieval split between "always injected" and "explicitly searched."

### Tier 0 — cold archive (searchable, lexical only)
Everything retired from any other tier lands in the `memory_archive` SQLite table — superseded/retracted medium entries, expired short-term rows, pruned messages, evicted profile facts (`src/db/repositories/memoryArchive.ts:1-16`). Search is **keyword, not semantic**: FTS5 with bm25 ranking when the SQLite build supports it, degrading to a `LIKE` scan ranked in JS by distinct-token hits otherwise (`memoryArchive.ts:112-119`, `267-353`). The query is tokenized and every FTS operator character is neutralized so user input can't inject `MATCH` syntax (`memoryArchive.ts:239-245`). Capped at 10,000 rows/handle with oldest-first eviction (`memoryArchive.ts:70`, `178-189`). This is the backing store for the `recall_memory` tool — the *only* path that reaches further back than what's unconditionally injected each turn (`src/agents/convo/tools.ts:211-226`).

### Tier 1 — short-term (24h, multi-entry, append-only within the window)
`memory_short` rows record every Ops research answer, media analysis, and Judge-flagged email from the last 24 hours (TTL `SHORT_TTL_MS = 24h`, content capped at 8,000 chars — `src/db/repositories/memoryShort.ts:15-32`). Written via `addShortTerm` with retry-then-log-loud-failure (best-effort policy, explicitly documented as acceptable to lose — `memoryShort.ts:1-9`, `70-105`). Read via `listShortTerm`, filtered to non-expired rows, newest first (`memoryShort.ts:107-140`). Swept hourly with a 48h grace period so a slipped run never loses a day of context, archiving before deleting (`memoryShort.ts:180-205`; scheduled from `src/db/retention.ts:105-121`). Rendered into the prompt as three sub-blocks — recent-research, a same-day digest, and flagged emails — with explicit "settled ground, never re-deliver" framing (`src/memory/shortTerm.ts:23-76`).

### Tier 2 — medium-term (durable, structured, capped, superseded-not-deleted)
Facts, directives, and "remember this" notes live as first-class entries in a human-readable flat file per user, `memories/<handle>/MEDIUM.md`, §-delimited with a trailing `<!-- mm id=... kind=... status=... -->` annotation per entry (`src/db/repositories/memoryMedium.ts:1-27`, format constants at `81-84`). Three kinds: `fact` (keyed slots like `comms_style`, `address_as` — `upsertFact`, `453-479`), `directive` (free-form behavior preferences, capped at 40 active — `addDirective`, `330-355`, cap at `65`), and `important_note` (explicit "remember this," capped at 20 — `addImportantNote`, `423-449`, cap at `66`). Retiring an entry (edit, cap-eviction, user retraction) **never deletes** — it flips `status` to `superseded`/`retracted`, sets a `supersededBy` pointer, and appends the old row to `MEDIUM.archive.md` plus the searchable `memory_archive` table (`enforceCap`, `314-328`; `appendArchive`, `192-216`). Failure policy is **fail-loud**: a durable write failure throws `MediumWriteError` after retries so the caller can say "hit a snag" instead of falsely confirming a save (`memoryMedium.ts:17-20`, `53-61`, `254-267`) — a sharper guarantee than mark-agent's groomer, which has no equivalent write-failure contract.

### Tier 3 — long-term (one free-form markdown document, LLM-rewritten, versioned)
A single per-user document, `memories/<handle>/LONG.md`, holding profile + how-to-talk-to-them prose, with **every accepted version snapshotted** under `revisions/LONG.vNNNN.md` (`src/db/repositories/memoryLong.ts:1-17`). Writes use **optimistic concurrency** — the writer must supply the version it read; a mismatch returns `null` and the caller re-reads and retries (`memoryLong.ts:86-121`). This doc is populated by `updateDossier` — an async, throttled (`THROTTLE_MS = 2 min`, `src/memory/dossier.ts:25`), Haiku-class LLM pass that takes the last 12 messages plus the existing dossier and returns a **full-document merge** (not a diff), capped at ~900 tokens / ~400 words, with a fixed section order and explicit instructions to capture only durable facts, never assistant scope/capability claims (`dossier.ts:164-176`, `DOSSIER_MAX_TOKENS` at `30`). It's called from `src/agents/convo/shared.ts:1456` after every reply. Because the LLM returns the *whole* document, a truncated response would silently delete the tail sections — guarded by `dossierUpdateUsable`, which refuses to persist a truncated rewrite and lets the next throttled pass retry from the last-good doc instead ("stale beats corrupted," `dossier.ts:191-201`, `293-315`). A `/forget` mid-merge race is fenced by an epoch counter so a merge that started before a wipe can't resurrect what was just deleted (`dossier.ts:118-135`, `216-257`).

### Write mechanism: LLM tool calls, not automatic extraction (mostly)
Unlike mark-agent's clustering-based groomer or Mem0's automatic fact-extraction pipeline, **almost every write in Irises is a live tool-call decision made by the front-line agent in the same turn**: `remember_user` (new personal-color facts, `src/agents/convo/tools.ts:17-28`), `set_preference` (name/timezone/comms-style/address-as/important-note, `tools.ts:94-105`), `update_directives` (add/update/remove a behavior preference, `tools.ts:171-190`), and `update_memory` (a *request*, not a direct write — it hands a reconciliation brief to the engine backend rather than touching Irises' own tiers, `tools.ts:192-209`). The one automatic, non-tool-call write is the throttled `updateDossier` pass described above — Irises' only real analog to mark-agent's background consolidation, except it summarizes/merges rather than clusters-and-dedupes.

### Recall mechanism: mostly unconditional injection, not retrieval
Every turn, `buildContextBlock` / `buildUserMemory` unconditionally assembles **all non-expired tiers** into the prompt — no relevance ranking, no similarity search, just recency + kind filters + TTL (`src/memory/dossier.ts:91-158`, `src/memory/wrappers.ts:714-735`). The assembly order is fixed and load-bearing: preamble → short → medium → (a "discovery scaffold" nudging what's still unknown) → long/flexible last, for recency (`wrappers.ts:665-707`). Each tier is wrapped in explicit "you must/must not" framing plus a data tag, and the whole design distinguishes three **authority classes** rather than the usual "tiers" framing: RIGID (persona, never overridable), FLEXIBLE (the one layer — long-doc + directives — allowed to retune style defaults), and DATA-ONLY (short/medium facts, which can inform an answer but never change behavior) (`wrappers.ts:1-56`). The only place anything resembling *search* happens is `recall_memory`, and as established above that's lexical FTS5/`LIKE`, not embeddings.

### Decay / eviction, summarized
- Short tier: 24h TTL, 48h sweep grace (`memoryShort.ts:30`, `src/db/retention.ts:116-121`).
- Medium tier: hard caps (40 directives / 20 notes) with oldest-active eviction to archive, never silent loss (`memoryMedium.ts:65-66`, `314-328`).
- Long tier: unbounded head doc (capped ~400 words by the LLM prompt, not by code) but revision files capped at the newest 50/handle (`src/db/retention.ts:33`, `67-100`).
- Cold archive: 10,000 rows/handle, oldest-first (`memoryArchive.ts:70`, `178-189`).
- Messages/sent/inbound: 7-day rolling window (`retention.ts:31`, `35-54`).
- `/forget`: the one true hard-delete path — wipes tiers and purges the archive for that handle, fenced against races by the forget-epoch mechanism above (`memory.ts:118-202`, `memoryArchive.ts:216-231`).

There *is* now a persisted, slowly-drifting relationship trait vector analogous to mark-agent's `relationship.js` — `relationship_climate` (`src/persona/climate.ts`, `src/memory/climateDrift.ts`): three handle-keyed register dials (ease / candor / playfulness, deliberately **no** trust dial) that a once-per-22h LLM eval nudges by ±1–2 points inside code-owned floors, ceilings and a rolling 6-point weekly budget, and that render as numberless prose inside the internal-weather block. It is the *slow* half of the pair described below. The *fast* half, `affect_state` (`src/db/repositories/affectState.ts:1-63`), persists a **per-chat mood trail for turn-to-turn continuity** (last computed status + a capped history of mood points) so a self-recursive meta-prompt carries forward — but per the repo's own memory notes it is recomputed fresh each turn from a Willcox-wheel mood model plus a 28-day cycle plus circadian rhythm, not additively learned from accumulated interaction the way mark-agent's warmth/trust/sarcasm dials are. It is a different mechanism solving a different problem (momentary affect continuity vs. a persisted relationship arc).

## 6. Comparison: each architecture vs. Irises, for a single-user companion

| Architecture | Better or worse than Irises here? | Why, for ONE user per instance | Worth borrowing? |
|---|---|---|---|
| **Vector / semantic** (Mem0) | **Worse on infra cost, better on paraphrase recall.** | A single user generates maybe dozens to low hundreds of durable memories over months — nowhere near the scale where vector indexing's real advantages (horizontal scale, million-row corpora) matter. Mem0's LoCoMo numbers are about full-context-vs-retrieval savings; Irises already avoids full-context stuffing structurally (tiers + caps), so most of that saving is moot here. What Irises *does* lose: `recall_memory`'s keyword search misses paraphrases a similarity search would catch. | **Narrow yes** — not a rearchitecture, but swapping `recall_memory`'s backend for a small local embedding model (Irises is already a single-VM SQLite deployment; a MiniLM-class model the way mark-agent runs it would fit) would fix its one real recall gap without touching the write side at all. |
| **Graph / temporal KG** (Zep/Graphiti) | **Worse at multi-hop, but Irises doesn't need multi-hop.** | Zep's advantage — reasoning over relationships between many entities across an org, correctly tracking who-superseded-whom — is built for exactly the kind of environment (enterprise assistants, many entities, complex org state) a single-user companion isn't. Irises' `superseded`/`retracted` + `supersededBy` pointer on medium-tier entries already gives it Zep's *core insight* (invalidate, never delete) in a much cheaper single-node form — it just can't answer a query that spans multiple facts/entities the way a graph traversal could. | **No** — the schema-design and extraction-reliability cost both blogs flag is real, and a companion with one user and a few dozen active facts has no multi-hop questions to answer. Not worth it at this scale. |
| **Episodic / working memory** (MemGPT/Letta) | **Roughly comparable, simpler and more fragile in different ways.** | Irises' `LONG.md` + throttled full-document LLM merge *is* an episodic "core memory" block in spirit — same goal (a coherent, self-edited standing picture), same characteristic risk (summarization drift, which Irises guards against via the truncation check but has no defense against gradual detail loss across many successive full-rewrites the way it would with an explicit diff-based update). Irises lacks MemGPT's formal paging API (the model itself deciding what moves to archival storage) — instead a fixed ~400-word cap and a hardcoded section-priority order do that job structurally. The short-tier (24h multi-entry log) is closer to a true episodic buffer than the dossier is. | **Maybe** — MemGPT's explicit move-to-archive function call (letting the *agent* decide what's worth demoting, rather than a hardcoded section-priority truncation) is a more graceful degradation than "later sections are dropped first." Irises' truncation-refusal guard is arguably already a stronger correctness property than MemGPT ships, though. |
| **Hybrid** (mark-agent's specific mix) | **Mixed: mark-agent recalls better, consolidates smarter, and models relationship depth; Irises writes and fails more safely.** | mark-agent's vector recall + LLM clustering-dedup (the "Hippocampus" groomer) is a more capable consolidation mechanism than Irises' exact-key `upsertFact` — Irises has nothing that clusters similar free-text notes and merges them the way mark-agent's groomer explicitly does. mark-agent's trait-drift relationship model (floor-clamped, anti-manipulation-guarded, ±0.05/step) is a genuinely distinct idea Irises has no equivalent to at all — Irises' `affect_state` is momentary mood, not an accreting relationship arc. Conversely, mark-agent (per the files reviewed) has no documented write-failure contract, no forget-epoch race guard, and no fail-loud/best-effort policy split — Irises is the more defensively engineered of the two on the durability axis. | **Yes, two things**: (1) a similarity-based merge/dedup pass for the medium tier's free-text notes (today only exact-key facts get supersede-in-place; notes/directives just accumulate to a cap and get FIFO-evicted, never merged); (2) a slowly-drifting, floor-clamped, anti-manipulation-guarded relationship-warmth dial, kept clearly distinct from the existing per-turn affect engine, as a genuinely new axis of personalization Irises doesn't have today. |

## Addendum (2026-08-28): what shipped

The "narrow yes" from the vector row of the table above is now implemented, and only that. `recall_memory` searches the cold archive with **two legs fused by reciprocal rank**: the existing lexical one (FTS5/bm25, or `LIKE` on a build without FTS5) and a new embedding one over a companion `memory_archive_embeddings` table. `score = 1/(60+lexRank) + 1/(60+vecRank)` — ranks, not scores, because bm25 and cosine are not on comparable scales.

What it deliberately is **not**:

- **Not a rearchitecture.** Only tier 0 (the cold archive) gained vectors. The short/medium/long tiers, every write path, and the unconditional per-turn context assembly are untouched — a turn costs exactly what it cost before.
- **Not a local model.** Vectors come from OpenRouter's OpenAI-shaped `/embeddings` endpoint on the key the app already has (`openai/text-embedding-3-small` at 512 dimensions by default), not from a bundled MiniLM. One less runtime to install and keep alive on a small VM; the cost is a provider round-trip per backfill batch, which is why embedding happens in an hourly background job and never on the per-turn path.
- **Not a graph.** The "no" from the graph row stands, unchanged and for the same reasons.
- **Not on by default.** `MEMORY_SEMANTIC_RECALL=off` ships in `deploy/app.env`. With the flag off — or the key missing — no embedder is registered and `searchArchive` returns byte-identical results to the pre-hybrid implementation, which is pinned by a deep-equal test against a forced lexical run.

Two design points worth recording, both about forgetting rather than recall:

1. **Vectors are a forget-leak surface.** A vector that outlives its archive row is a deleted memory still semantically reachable — so `memory_archive_embeddings.archive_id` carries `ON DELETE CASCADE`, `purgeArchiveFor` deletes vectors explicitly *before* the parent rows rather than trusting the pragma, and there are regression tests for all four ways a row leaves the archive (purge, per-insert cap eviction, the daily sweep, the test reset).
2. **The backfill is fenced by the forget epoch**, the same mechanism the dossier rewrite uses: the epoch is read before the (slow, awaited) embedding call and re-read before writing, so a `/forget` landing mid-flight cannot have its wipe undone by vectors computed from the content it just deleted.

Relevant source: `src/db/repositories/memoryArchiveVectors.ts` (storage + backfill), `src/db/repositories/memoryArchive.ts` (fusion), `src/llm/embed.ts` (the provider call), `src/memory/semanticRecall.ts` (wiring).
